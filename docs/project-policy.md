## Purpose

Метою цієї політики є встановлення обов'язкових вимог та правил безпечної розробки мобільного застосунку **Writer Editor**, спрямованих на запобігання витоку даних користувачів, забезпечення цілісності авторського контенту (книг, розділів, метаданих), захист від SQL-ін'єкцій та пошкодження форматів при експорті, а також мінімізацію ризиків вразливостей у сторонніх залежностях.

**Основні безпекові цілі проєкту:**
- Забезпечення цілісності та конфіденційності авторських текстів у локальній базі даних SQLite.
- Унеможливлення SQL-ін'єкцій при роботі з локальним сховищем `expo-sqlite`.
- Захист згенерованих OpenXML-контейнерів (`.docx`) від XML-ін'єкцій та пошкодження структури.
- Захист файлової системи від атак типу Path Traversal при формуванні назв експортованих файлів.
- Дотримання принципу Offline-First та мінімізація збору даних без необґрунтованої передачі інформації у зовнішні мережі.

Політика поширюється на всі етапи життєвого циклу застосунку: проектування, розробку, тестування, збірку релізних артефактів та підтримку.

## Scope

Політика поширюється на:
- Увесь вихідний код мобільного застосунку в репозиторії (`App.js`, папка `src/`: екрани, UI-компоненти, шар доступу до даних DAL, сервіси експорту, навігація, хуки, конфігурація тем та локалізацій).
- Конфігураційні файли проєкту (`app.json`, `package.json`, `package-lock.json`, `.babelrc`).
- Інструменти та конфігурації автоматизованого тестування і лінтингу.
- Проектну документацію в папці `docs/`.

**Учасники, зобов'язані дотримуватися політики:**
- Розробники та рев'юери проєкту.
- ШІ-агенти та автономні помічники (наприклад, Antigravity / GitHub Copilot), що виконують генерацію або модифікацію коду.

**Явні виключення зі скоупу:**
- Внутрішня реалізація ядра операційних систем (Android OS / iOS Security Sandbox).
- Апаратна безпека мобільних пристроїв користувача.
- Внутрішня реалізація зовнішніх застосунків (месенджери, поштові клієнти, хмарні диски), у які користувач передає згенеровані файли через системне меню `Expo Sharing`.

## Roles and Responsibilities

- **Власник проєкту / Lead Developer:**
  - Затверджує політику безпеки, модель загроз та специфікацію вимог.
  - Погоджує винятки з вимог безпеки та приймає залишковий ризик.
  - Контролює процес релізу та затверджує критичні зміни в архітектурі.

- **Розробник (Developer):**
  - Відповідає за строге дотримання правил безпечної реалізації коду (параметризація SQL, екранування XML, санітизація імен файлів).
  - Забезпечує обробку помилок у UI без виведення системних стек-трейсів.
  - Проводить попереднє тестування власних змін та оновлює документацію.

- **Рев'юер (Reviewer):**
  - Перевіряє Pull Request на відповідність цій політиці безпеки.
  - Блокує злиття коду при виявленні непараметризованих SQL-запитів, прямих маніпуляцій з неуправльованими файловими шляхами чи хардкоду секретів.

- **ШІ-агент (AI Coding Assistant):**
  - Виконує генерацію та рефакторинг коду СТРОГО відповідно до правил цієї політики.
  - Не має права самостійно послаблювати безпекові вимоги, видаляти модальні вікна підтвердження або міняти параметризовані SQL-запити на рядкову конкатенацію.

## Security Principles

- **Offline-First & Local Data Sovereignty:** Усі дані користувача зберігаються виключно локально на пристрої у БД SQLite (`writer-editor.db`). Застосунок функціонує без вимоги мережевого з'єднання та не надсилає фонову телеметрію.
- **Least Privilege (Принцип найменших привілеїв):** Застосунок запитує лише мінімально необхідні системні дозволи ОС (наприклад, доступ до системного вибору зображень `Expo ImagePicker` для обкладинки книги).
- **Defense in Depth (Глибока оборона):** Вхідні дані перевіряються та обробляються на кількох рівнях: валідація формату в UI, очищення в сервісах (`escapeXml`, `sanitizeFileName`) та параметризація на рівні Data Access Layer (`client.js`).
- **Secure by Default & Fail Securely:** При збоях у роботі з базою даних або файловою системою застосунок не падає ("вилітає"), а повертається до безпечного стану з відображенням зрозумілого повідомлення користувачеві.
- **Minimize Attack Surface:** Мінімізація зовнішніх npm-залежностей. Відсутність невикористовуваних нативних модулів або відкритих мережевих портів.
- **No Secrets in Source Code:** Заборонено зберігати будь-які токени, ключі або секрети у вихідному коді чи в історії контролю версій Git. Якщо у майбутньому додаватимуться зовнішні сервіси, ключі мають передаватися через змінне оточення (`.env`).
- **Explicit Trust Boundaries:** Чітке розмежування меж довіри між недовіреним вводом користувача, WebView-редактором Rich Text, пісочницею додатку та системним меню поширення файлів.

## Secure Development Environment

- **Контроль версій та Git Workflow:**
  - Прямі зміни в захищену гілку `main` заборонені.
  - Усі зміни інтегруються через Pull Requests з обов'язковим рев'ю.
  - Використовуються стандартизовані префікси комітів: `[FEAT]`, `[FIX]`, `[DOCS]`, `[POLICY]`, `[SEC]`.
- **Управління секретами:**
  - Файли конфігурації оточення (`.env`), тимчасові файли та збірки додаються у `.gitignore`.
- **Робота із залежностями:**
  - Фіксація версій пакетів у `package-lock.json`.
  - Додавання нової npm-залежності вимагає перевірки її популярності, ліцензії (MIT/Apache 2.0) та відсутності відомих вразливостей.
  - Обов'язкове виконання `npm audit` перед збіркою релізів.
- **Використання ШІ-інструментів:**
  - Інструкції та обмеження з політики передаються в контекст ШІ-агентів. Вигенерований ШІ код підлягає обов'язковій валідації на відсутність анти-патернів.

## Software Protection

- **Захист вихідного коду:** Репозиторій розміщено на захищеному хостингу (GitHub) з обмеженням прав доступу.
- **Цілісність релізних артефактів:** Релізні збірки (APK/AAB/IPA) формуються через інструментарій Expo (EAS Build або локальний Expo CLI) із використанням захищених цифрових підписів і ключів підписання.
- **Захист ключів підписання:** Приватні ключі підписання (Android Keystore / iOS Distribution Certificates) зберігаються поза репозиторієм у захищеному сховищі ключів.
- **Мінімізація чутливих даних у логах:** Заборонено виводити повні тексти книг, розпарсені структури чи системні стеки помилок у підсумкові виробничі логи.

## Secure Implementation

- **Валідація та санітизація даних:**
  - **Текст користувача:** Текст перед формуванням XML-структур у файлі `.docx` обов'язково обробляється функцією `escapeXml()`, яка замінює спецсимволи `&`, `<`, `>`, `"`, `'` на відповідні XML-сутності.
  - **Назви файлів:** Для запобігання Path Traversal при збереженні назви книг очищаються функцією `sanitizeFileName()`, яка видаляє управляючі символи та спецсимволи ОС (`/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`).
  - **Rich Text HTML:** Текст із `RichEditor` під час конвертації в звичайний текст проганяється через утиліту `richHtmlToPlainText()`.
- **Безпечна робота з базою даних (SQLite):**
  - Пряма конкатенація рядків у SQL-запитах **СТРОГО ЗАБОРОНЕНА**.
  - Усі SQL-запити в `src/database/client.js` виконуються виключно із застосуванням параметризованих запитів з плейсхолдерами `?`.
  - Для забезпечення цілісності та запобігання блокуванням БД при ініціалізації вмикається режим `PRAGMA journal_mode = WAL;` та вмикається підтримка зовнішніх ключів `PRAGMA foreign_keys = ON;`.
- **Безпека WebView (Rich Text Editor):**
  - WebView-компонент `react-native-pell-rich-editor` ізолюється від нативного мосту та локальної файлової системи пристрою.
- **Обробка помилок та логування:**
  - Усі виклики SQLite та файлової системи загортаються вблоки `try/catch`.
  - Користувачеві відображаються локалізовані та зрозумілі повідомлення про помилку через UI-компоненти (Toast / Alert), без демонстрації сирих помилок бази даних чи стек-трейсів.

## Security Verification

- **Code Review:** Кожен Pull Request перевіряється на відсутність порушень правил безпечної реалізації (усі SQL-запити перевіряються на параметризацію, а операції з файлами — на санітизацію шляхів).
- **Статичний аналіз коду:** Використання ESLint для перевірки синтаксису, потенційних багів та невикористовуваного коду.
- **Сканування залежностей:** Виконання `npm audit` у процесі розробки та перед кожним релізом. Виявлені вразливості рівня `High` та `Critical` підлягають негайному усуненню.
- **Автоматизоване та ручне безпекове тестування:**
  - Тестування граничних значень: введення в назви та текст символів кавички, спецсимволів XML, SQL-ін'єкцій (`' OR 1=1 --`), довгих рядків.
  - Перевірка коректності експорту та відкриття згенерованих `.docx` файлів у MS Word / LibreOffice.
  - Перевірка функціонування модальних вікон підтвердження `ConfirmActionModal` при видаленні книг та розділів.
- **Release Gate:** Реліз блокується, якщо в коді наявні незатверджені винятки або непідтверджені вразливості залежностей високого рівня.

## Vulnerability Management

- **Джерела виявлення:** Результати `npm audit`, сповіщення GitHub Dependabot, результати внутрішнього тестування або звернення користувачів.
- **Реєстрація та класифікація:** Усі виявлені дефекти безпеки реєструються в баг-трекері із присвоєнням рівня критичності:
  - **Critical:** Можливість пошкодження всієї БД SQLite, виконання довільного коду в WebView, витік даних.
  - **High:** XML-ін'єкція у експортований файл, Path Traversal при збереженні.
  - **Medium/Low:** Некоректне відображення помилки, неоптимальний Debounce.
- **Строки виправлення:**
  - Вразливості рівня `Critical` та `High` усуваються протягом 48 годин у хотфікс-гілках.
  - Вразливості `Medium` та `Low` усуваються у плановому порядку в наступному спринті/релізі.
- **Аналіз причин (Root Cause Analysis):** Після усунення критичної вразливості проводиться аналіз причин її виникнення, а за потреби оновлюється модель загроз та правила цієї політики.

## Privacy Policy

Правила обробки персональних та чутливих даних користувачів у мобільному застосунку **Writer Editor** деталізовано в окремому документі:

**[docs/privacy-policy.md](privacy-policy.md)** — Політика конфіденційності (Privacy Policy).

**Короткий витяг з політики конфіденційності:**
- Застосунок працює за принципом **Offline-First**: усі книги, розділи, чернетки та текстова статистика зберігаються виключно в локальній пісочниці пристрою у файлі `writer-editor.db`.
- Застосунок не збирає персональні дані, не має серверної частини для синхронізації та не використовує трекери аналітики чи реклами.
- Передача згенерованих файлів експорту виконується виключно за явним ініціюванням користувача через системний діалог `Expo Sharing`.

## Exceptions

- **Підстави для винятку:** Відступ від вимог цієї політики допускається лише в разі наявності технічної неможливості виконання вимоги або якщо виконання вимоги унеможливлює функціонування ключової бізнес-логіки.
- **Процедура погодження:** Автор зміни подає письмове обґрунтування з описом ризику, запропонованими компенсуючими заходами та строком дії винятку.
- **Затвердження:** Виняток вважається прийнятим лише після письмового затвердження Власником проєкту (Lead Developer).
- **Облік:** Усі діючі винятки фіксуються в цьому розділі документу із зазначенням строку їх повторного перегляду.

*Наразі активних винятків із політики безпеки немає.*

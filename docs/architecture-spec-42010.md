## 1. Вступ та системний контекст

Цей документ містить архітектурний опис мобільного застосунку **Writer Editor**, розроблений відповідно до стандарту **ISO/IEC/IEEE 42010:2022**. Документ визначає ключові архітектурні точки зору (Viewpoints), розбиття системи на шари, взаємодію компонентів та межі довіри (Trust Boundaries).

Застосунок проектується на базі кросплатформеного фреймворку React Native / Expo і працює за принципом **Client-Side Only / Offline-First**: усі дані обробляються та зберігаються локально на мобільному пристрої.

## 2. Архітектурні точки зору (Architectural Viewpoints)

### 2.1 Context Viewpoint (Контекстна точка зору)

Контекстна точка зору описує взаємодію застосунку з користувачем та нативними сервісами операційної системи мобільного пристрою:

- **Користувач / Автор:** Взаємодіє з мобільним додатком через графічний інтерфейс користувача (UI).
- **Writer Editor App:** Виконує бізнес-логіку, підраховує статистику слів, обробляє форматований текст.
- **Локальна БД SQLite (`writer-editor.db`):** Зберігає книги, розділи та сесії написання через параметризовані SQL-запити.
- **Файлова система ОС (Expo FileSystem):** Використовується для тимчасового збереження експортованих `.docx` та `.txt` файлів у каталогах `documentDirectory` або `cacheDirectory`.
- **Галерея зображень (Expo ImagePicker):** Нативний модуль для вибору обкладинки книги.
- **Системний діалог поширення (Expo Sharing):** Нативний шар ОС для передачі файлів в інші додатки (месенджери, пошта, хмарні диски).

---

### 2.2 Component & Layered Viewpoint (Пошарова компонента точка зору)

Систему сплановано у вигляді 5 ізольованих шарів:

1. **Presentation Layer (Шар інтерфейсу користувача):**
   - **Screens:** `LockScreen`, `LibraryScreen`, `BookDetailsScreen`, `BookMetaFormScreen`, `BookChaptersScreen`, `EditorScreen`, `BookStatsScreen`, `SettingsScreen`, `InfoScreen`.
   - **Components:** `ConfirmActionModal`, `ExportFormatModal`, `RenameChapterModal`, `PopupMenu`, `StatBadge`, `Toast`.
   - **Theme & Localization:** `ThemeProvider`, `LocalizationProvider`.
2. **Navigation & Session Layer (Шар навігації та управління сесією):**
   - `AppNavigator` на базі React Navigation Stack.
   - `App.js` контроль стану сесії `isAuthenticated` та автоблокування при згортанні додатка у фоновий режим (`AppState`).
3. **Business Logic & Security Services Layer (Сервісний шар бізнес-логіки та безпеки):**
   - `cryptoService.js` — криптографічний сервіс автентифікованого симетричного шифрування (AEAD AES-256-GCM), верифікація Auth Tag (контроль цілісності), генерація 96-бітних CSPRNG Nonce, деривація ключів через PBKDF2 (HMAC-SHA256, 10 000+ ітерацій) та управління життєвим циклом ключів.
   - `authService.js` — сервіс автентифікації: хешування PIN (bcryptjs, cost 10), перевірка спроб, захист від брутфорсу (блокування на 45 сек після 5 помилок) та біометрія (`expo-local-authentication`).
   - `bookExport.js` — генерація та експорт файлів `.docx` (через `jszip`) та `.txt`.
   - Утиліти обробки тексту: `richHtmlToPlainText`, `escapeXml`, `sanitizeFileName`, `countWords`.
4. **Data Access Layer (Шар доступу до даних — DAL):**
   - `src/database/client.js` — модуль ініціалізації SQLite, прозоре шифрування та дешифрування поля `body`/`content` через `cryptoService`, створення схем таблиць (`books`, `chapters`, `writing_sessions`, `auth_settings`), атрибутів ABAC (`is_locked`) та виконання параметризованих SQL-запитів.
5. **Native OS & Storage Layer (Шар нативних модулів ОС):**
   - `expo-sqlite`, `expo-local-authentication`, `expo-file-system`, `expo-sharing`, `expo-image-picker`.

### 2.3 Модель керування доступом RBAC / ABAC

Система підтримує комбіновану модель розмежування доступу:

1. **RBAC (Role-Based Access Control — Модель ролей):**
   - **Unauthenticated (Неавторизований):** Початковий стан додатку при ввімкненому PIN-захисті. Доступ до екранів бібліотеки та редактора заблоковано, відображається `LockScreen`.
   - **Authenticated Author (Авторизований автор):** Стан після успішного введення майстер-PIN або проходження біометрії. Надає повний доступ до навігації додатком.

2. **ABAC (Attribute-Based Access Control — Модель атрибутів):**
   - Атрибут об'єкта `chapter.is_locked`: Окремий розділ може бути позначений як захищений (`is_locked = 1`).
   - Контекстне правило доступу: При спробі відкрити розділ із `is_locked = 1` система запитує повторне підтвердження PIN-коду автора в модальному вікні перед відкриттям екрана редагування.

### 2.4 Cryptographic Architecture & Strategy Viewpoint (Криптографічна стратегія)

Для захисту конфіденційності та гарантування цілісності авторського контенту (Data-at-Rest) впроваджено багатошарову криптографічну стратегію:

```
+-------------------------------------------------------------+
| Presentation Layer (EditorScreen / BookChaptersScreen)      |
| [Plaintext HTML / Rich Text в оперативній пам'яті UI]       |
+-------------------------------------------------------------+
                              |
                     save / retrieve
                              v
+-------------------------------------------------------------+
| Data Access Layer (src/database/client.js)                  |
| - transparent encrypt before SQL UPDATE                     |
| - transparent decrypt after SQL SELECT                      |
| - відкриті метадані: words_count, chars_count, title        |
+-------------------------------------------------------------+
                              |
                      encrypt / decrypt
                              v
+-------------------------------------------------------------+
| Crypto Service (src/services/cryptoService.js)              |
| - Алгоритм: AES-256-GCM (AEAD)                              |
| - CSPRNG Nonce Generator (96-bit унікальний IV)            |
| - Auth Tag Generator & Validator (128-bit MAC)             |
| - Key Derivation: PBKDF2 (HMAC-SHA256, 10,000 rounds)      |
+-------------------------------------------------------------+
                              |
                   store / fetch ciphertext
                              v
+-------------------------------------------------------------+
| SQLite Storage (writer-editor.db -> chapters table)         |
| [ENC:v1:AES-256-GCM:<IV>:<Ciphertext>:<AuthTag>]            |
+-------------------------------------------------------------+
```

#### 2.4.1 Формат збереження шифротексту
Усі зашифровані тексти зберігаються у стовпці `body` таблиці `chapters` у вигляді стандартизованого рядкового контейнера:
```
ENC:v1:AES-256-GCM:<IV_HEX>:<CIPHERTEXT_HEX>:<AUTH_TAG_HEX>
```
Компоненти формату:
- **`ENC:v1:AES-256-GCM:`** — фіксований префікс протоколу та версії алгоритму, що дозволяє DAL автоматично розрізняти зашифрований текст від відкритого (забезпечує зворотну сумісність з існуючими записами).
- **`IV_HEX`** — 96-бітний (12 байтів) криптографічно випадковий вектор ініціалізації (CSPRNG), унікальний для кожного збереження.
- **`CIPHERTEXT_HEX`** — симетрично зашифрований текст розділу (кодування UTF-8).
- **`AUTH_TAG_HEX`** — 128-бітна (16 байтів) мітка автентичності Galois/Counter Mode. При невідповідності хоча б одного біта дешифрування негайно відхиляється.

#### 2.4.2 Життєвий цикл криптографічних ключів (Key Lifecycle)
1. **Генерація (Key Generation):** 256-бітний симетричний ключ генерується за допомогою CSPRNG або виводиться з солі та майстер-PIN автора через PBKDF2 (HMAC-SHA256, 10 000 ітерацій, 128-бітна криптографічна сіль).
2. **Збереження (Key Storage):** Ключ та параметри солі зберігаються у внутрішній захищеній таблиці `auth_settings` або апаратному SecureStore пристрою.
3. **Використання (Key Usage):** Ключ утримується в захищеному замиканні модуля `cryptoService` виключно в оперативній пам'яті процесу під час роботи застосунку; не передається в логи та не експортується в зовнішні файли.
4. **Ротація (Key Rotation):** При зміні авторського PIN-коду викликається метод `cryptoService.rotateKey(newPin)`, який перегенеровує ключ із новою сіллю.
5. **Знищення (Key Revocation / Disposal):** При скиданні або видаленні захисту ключ та сіль безповоротно видаляються з локального сховища.

### 2.5 Security & Trust Boundaries Viewpoint (Межі довіри та безпеки)

В архітектурі системи виділяються наступні межі довіри (Trust Boundaries):

1. **TB-1: Untrusted User Input Boundary (Межа вводу користувача):**
   - Межа між користувачем та UI-компонентами. Всі введені дані вважаються потенційно некоректними і вимагають валідації та санітизації.
2. **TB-2: WebView / Editor Boundary (Межа візуального редактора):**
   - Межа між JS-рушієм додатка та вбудованим WebView компонента `RichEditor`. HTML-текст при отриманні з WebView проганяється через очищення.
3. **TB-3: Cryptographic & Storage Boundary (Межа криптографічного захисту БД):**
   - Чітка межа між Data Access Layer та файлом БД `writer-editor.db`. Будь-який прямий доступ до файлу SQLite ззовні (наприклад, через рутований пристрій або вилучення дампу пам'яті) надає зловмиснику лише шифротексти без можливості прочитати зміст розділів або сфальсифікувати їхній вміст через контроль Auth Tag.
4. **TB-4: External OS Share Boundary (Межа передачі файлів у зовнішні додатки):**
   - Межа при передачі файлів через системний `Share Sheet`. Тимчасові файли очищаються з кешу при повторному експорті.

### 2.6 License Verification Viewpoint (Верифікація ліцензії публічним ключем)

Ліцензування за моделлю Freemium реалізовано сервісом `src/services/licenseIntegrityService.js` на основі **асиметричної криптографії (Public Key Verification)**: підписувати ліцензії може лише розробник (приватний ключ), а застосунок лише перевіряє підпис (публічний ключ).

```
 Сторона розробника (поза застосунком)          Клієнт (Writer Editor)
+------------------------------------+       +------------------------------------------+
| Private Key (HSM / KMS / офлайн)   |       | DEVELOPER_PUBLIC_KEY_PEM (RSA-2048)      |
| sign(SHA-256("LICv1|userId|tier|   | ----> | verify(signature) у licenseIntegrity-    |
|      expiresAt"))                  | token | Service -> tier: FREE | PRO               |
+------------------------------------+       |   -> перевірка expiresAt                 |
   ніколи не потрапляє в клієнт              |   -> tierHasFeature(tier, feature)       |
                                             +------------------------------------------+
```

**Ліцензійний об'єкт:** `{ userId, tier: 'FREE' | 'PRO', expiresAt, signature }`; токен активації — base64(JSON). Зберігається в `auth_settings` (ключ `license_object`), але **довіра до нього не базується на самому факті зберігання**: підпис повторно перевіряється при кожному зверненні (`getLicenseStatus`), тому пряма правка БД (наприклад, зміна `tier` на `PRO`) не надає прав.

**Матриця прав (Freemium):**

| Функція | Free | Pro |
|---|:---:|:---:|
| Базове редагування книг (`EDIT_BOOKS`) | ✅ | ✅ |
| Експорт `.txt` (`EXPORT_TXT`) | ✅ | ✅ |
| Експорт `.docx` (`EXPORT_DOCX`) | — | ✅ |
| Детальна статистика (`DETAILED_STATS`) | — | ✅ |
| Шифрування розділів (`CHAPTER_ENCRYPTION`) | — | ✅ |

**Контроль цілісності (MDC):**
- `computeSha256Hex` / `verifyDataIntegrity` — SHA-256 хеш і порівняння за постійний час; `buildHashManifest` формує sidecar-файл `.sha256`.
- `verifyStorageIntegrity` — верифікація AEAD Auth Tag усіх зашифрованих розділів у SQLite.
- `verifyEnvironmentIntegrity` — звірка SHA-256 дайджесту конфігурації (публічний ключ + матриця прав) з еталонним значенням `EXPECTED_CONFIG_DIGEST`, перевірка `Object.freeze`, відсутність підвищення прав Free-тарифу; попередження про dev-збірку (`__DEV__`).

**Обмеження моделі загроз:** код JS-клієнта може бути змінений зловмисником на рутованому пристрої (патч перевірки або заміна публічного ключа). Перевірка конфігурації — захист рівня best-effort, що підвищує вартість атаки; фундаментальний захист забезпечується Code Signing релізних збірок (див. `docs/project-policy.md`) та неможливістю підробити підпис без приватного ключа.

### 2.7 Client-Server Trust Boundary (Клієнт-серверна модель довіри, ЛР №6)

```
┌──────── НЕДОВІРЕНЕ СЕРЕДОВИЩЕ ────────┐   TLS 1.3    ┌────────── ДОВІРЕНА ЗОНА ──────────┐
│ Мобільний клієнт (RN/Expo)            │ ───────────► │ API-сервер (server/apiServer.js)  │
│ apiClient.js · SecureStore · SQLite   │  Bearer JWT  │ перевірка токена · RBAC · ownerId │
│ AES-256-GCM шифрування до відправки   │ ◄─────────── │ сховище користувачів · refresh    │
└───────────────────────────────────────┘ 200/401/403  └───────────────────────────────────┘
```

Клієнт може бути рутованим, пропатченим або підмінений скриптом, тому **будь-яка клієнтська перевірка — лише UX-підказка**. Межа довіри проходить по мережевому каналу: усе, що надходить із клієнта (тіло, заголовки, прапорці ролей, `ownerId`), вважається недостовірним.

**Розподіл відповідальності:**

| Завдання | Клієнт | Сервер |
|---|---|---|
| Автентифікація | Збір облікових даних, зберігання токенів у SecureStore | Перевірка пароля (scrypt + сіль), видача токенів, обмеження спроб входу (429) |
| Авторизація (RBAC) | Лише приховування кнопок (UX) | **Єдине джерело істини**: `tier` береться з підписаного токена, `403` для невідповідної ролі |
| Власність даних | Не визначає | `ownerId` = `token.sub`; вибірка лише за власником (захист від IDOR) |
| Конфіденційність бекапів | Шифрує розділи AES-256-GCM до відправки (ключ не залишає пристрій) | Зберігає лише конверт `ENC:v1:AES-256-GCM:…`, відхиляє відкритий текст |
| Транспорт | Лише `https://` (http — лише dev/localhost) | TLS 1.3, HSTS у production |

**Життєвий цикл токенів:**

1. `POST /api/auth/login` → `access_token` (HS256 JWT: `sub`, `tier`, `typ`, `iat`, `exp`, `jti`; TTL 15 хв) та `refresh_token` (непрозорий 256-бітний CSPRNG, TTL 7 діб; сервер зберігає лише SHA-256 хеш).
2. Кожен захищений ендпоінт перевіряє: формат `Bearer`, фіксований алгоритм `HS256` (відхиляє `alg=none`), HMAC у сталому часі, `exp`, `typ=access`, коректність `tier`.
3. Клієнт отримує `401` → одноразово викликає `POST /api/auth/refresh` (single-flight) і повторює запит; невдача → очищення SecureStore та вихід із сесії.
4. **Ротація:** кожен refresh-токен одноразовий; сервер видає нову пару в тій самій «сім'ї» і перечитує `tier` зі свого сховища (зміна тарифу діє після оновлення).
5. **Replay-захист:** повторне пред'явлення вже використаного refresh-токена вважається крадіжкою — уся сім'я токенів відкликається, потрібен повторний вхід. Короткий TTL access-токена обмежує вікно повторного відтворення викраденого токена; refresh-токен не приймається як Bearer.

**Захист від IDOR:** `POST /api/sync/books` ігнорує `ownerId` із тіла й записує `token.sub`; `GET` фільтрує `ownerId === token.sub`; спроба перезапису чужого `id` повертає `404` (не розкриває існування ресурсу).

**ADR-8 (Серверна авторизація замість клієнтської):** права Pro для хмарних функцій перевіряються на сервері за підписаним токеном; локальна ліцензія (ADR-6) керує лише офлайн-функціями. **ADR-9 (HMAC-JWT на сервері):** симетричний ключ безпечний, бо він ніколи не залишає сервер (на відміну від клієнта, ADR-6); секрет задається через `JWT_SECRET`.

### 2.8 Logging, Monitoring & Backup Viewpoint (Журналювання, моніторинг та резервне копіювання, ЛР №7-8)

**Зацікавлені сторони та питання (concerns):** адміністратор/аудитор (хто, що, коли зробив і з яким результатом), власник проєкту (виявлення атак у реальному часі), користувач (відновлення рукописів після збою). Точка зору покриває вимоги FR-8.x, NFR-I-10, NFR-A-4..A-6.

#### 2.8.1 Підсистема структурованого логування (`server/logger.js`)

```
HTTP-запит ──► apiServer.handler ──► requestId=UUID, ctx{actor,ip,component,action,resource}
                    │                               │
                    ▼                               ▼ (res.on 'close')
              route/handlers ───────────► logRequest ──► Logger.log() ──► sanitize() ──► logs/security.log (JSON Lines)
                    │                                          │                     └─► stdout (консоль)
                    └─► Monitor.bump / recordFailedLogin ◄─────┘        ротація: > 1 МБ => security-<ts>.log
                              │
                              └─► GET /api/admin/metrics (ADMIN)  +  алерти WARNING / CRITICAL у журнал
```

**Формат події** (один JSON-об'єкт на рядок, UTF-8):

| Поле | Опис |
|---|---|
| `timestamp` | ISO 8601 UTC, `new Date().toISOString()` (`2026-11-18T14:05:07.427Z`) — єдиний часовий стандарт для зіставлення подій із різних компонентів |
| `level` | `DEBUG` · `INFO` · `WARNING` · `ERROR` · `CRITICAL` |
| `requestId` | UUID v4, згенерований сервером на початку запиту; повертається клієнту в `X-Request-Id` |
| `component` | `AuthService`, `SyncAPI`, `ExportService`, `MonitoringService`, `HttpServer`, `BackupManager` |
| `actor` | `{ id, ip }` — `sub` із перевіреного токена (або `anonymous`/ім'я для спроб входу) та IP-адреса |
| `action` / `resource` | напр. `POST /api/sync/books` / `book:<id>`; для подій безпеки — `anomaly.bruteforce_detected`, `auth.refresh_replay_detected`, `backup.restore` |
| `outcome` | `SUCCESS` · `DENIED` (401/403/404/429, відмова політики) · `ERROR` (помилка запиту/сервера) |
| `context` | додаткові санітизовані поля: HTTP-статус, `durationMs`, код помилки, версія ресурсу тощо |

Приклад:
```json
{"timestamp":"2026-11-18T14:05:07.427Z","level":"WARNING","requestId":"7d0c1a52-9c0b-4a3e-8d57-0f0b1c6b6a11","component":"ExportService","actor":{"id":"u-alice","ip":"::ffff:127.0.0.1"},"action":"POST /api/export/docx-cloud","resource":"/api/export/docx-cloud","outcome":"DENIED","context":{"requiredTier":"PRO","actualTier":"FREE","method":"POST","status":403,"durationMs":1,"error":"PRO_REQUIRED"}}
```

**Кореляція за `requestId`.** Усі записи, що належать одному запиту (підсумковий запис запиту, алерт брутфорсу, подія replay-атаки), несуть той самий `requestId`; відповідь містить його в `X-Request-Id`, тож інцидент за скаргою клієнта знаходиться за одним ідентифікатором (`grep <uuid> logs/security.log`). Ідентифікатор генерується **лише сервером**: значення з клієнтського заголовка ігнорується (захист від log forging / Repudiation, STRIDE-R).

**Санітизація (Sanitization).** Кожен запис проходить `sanitize()` до запису у файл і консоль: (1) ключі `password`, `pin`, `client_secret`, `secret`, `authorization`, `*password`, `*secret` → `***REDACTED***`; (2) ключі `*token` (`access_token`, `refresh_token`) → перші 6 символів + `***REDACTED***` (достатньо для ідентифікації, недостатньо для використання); (3) у вільному тексті маскуються `Bearer …`, JWT-подібні рядки та пари `password=…`; (4) глибина/цикли/довжина рядків обмежені. Тіла запитів у журнал не пишуться взагалі — лише явно обрані поля; санітизація є другим рубежем (defense in depth). Тексти книг (шифротекст) у журнал не потрапляють.

**Ротація.** Перед кожним записом перевіряється розмір `logs/security.log`: якщо `розмір + новий рядок > 1 МБ`, файл перейменовується в `security-<UTC-мітка>.log`, створюється новий; зберігається не більше 5 архівів (найстаріші видаляються). Збій запису журналу не перериває обробку запиту (журнал не повинен ставати вектором DoS). Рекомендація для production: права `0600` для каталогу `logs/`, додавання лише (append-only) та пересилання на окремий хост журналів.

**Моніторинг та виявлення аномалій (`createMonitor`).** Лічильники: усього запитів, розподіл за статусами, окремо 401 / 403 / 429 / 5xx, невдалі входи. Детектор брутфорсу веде ковзне 60-секундне вікно окремо за IP та за username: ≥ 5 невдалих спроб → подія `WARNING`, ≥ 10 → `CRITICAL` (`anomaly.bruteforce_detected`, подія пишеться при зміні рівня, а не на кожну спробу). Снапшот доступний через `GET /api/admin/metrics` лише ролі `ADMIN` (роль береться з підписаного токена, `403 ADMIN_REQUIRED` для решти).

#### 2.8.2 Стратегія резервного копіювання та відновлення (`scripts/backupManager.js`)

| Аспект | Рішення |
|---|---|
| Що копіюється | `data/` (`writer-editor.db` — експорт локальної SQLite-бази, `server-store.json`), `app.json`, `package.json`, `package-lock.json`, `logs/security.log` (аудит). Вміст БД і сховища вже є шифротекстом `ENC:v1:AES-256-GCM:…`, тому копії не розкривають рукописи; ключ шифрування (SecureStore / `JWT_SECRET`) **не** входить у копію й зберігається окремо |
| Формат | `backups/backup_<UTC-мітка>/{manifest.json, manifest.sha256, files/…}` |
| MDC | SHA-256 кожного файлу (`manifest.json`: `path`, `size`, `sha256`) та SHA-256 самого маніфесту (`manifest.sha256`) |
| Відновлення | **Fail-closed**: 1) верифікація маніфесту й усіх файлів (хеш, розмір, відсутні/сторонні файли, path traversal); 2) за будь-якої невідповідності — `CRITICAL` в журнал, код виходу 2, нічого не змінюється; 3) атомарний запис (tmp → rename), пошкоджені версії зберігаються в `backups/pre_restore_<ts>/`; 4) повторна перевірка SHA-256 та структурна валідація (SQLite-заголовок, JSON) |
| Аудит | Операції `backup.create/verify/restore/prune` пишуться тим самим форматом із `component=BackupManager` |
| Перевірка | `node scripts/dr_simulation.js` — backup → інцидент → відхилення підробленої копії → restore → порівняння хешів |

Розташування копій, правило 3-2-1, RPO/RTO та план DR визначені в `docs/project-policy.md` (розділ «Backup and Disaster Recovery»). Цілісність копій від зловмисної підміни (атакуючий з доступом до каталогу може змінити і файли, і маніфест) у перспективі підсилюється підписом маніфесту (HMAC/RSA) та зберіганням копії на носії з запретом перезапису — це відображено як залишковий ризик.

## 3. Опис потоку даних при ключових операціях

### 3.1 Потік автозбереження тексту розділу з автентифікованим шифруванням:
1. Користувач вводить текст у `EditorScreen` -> спрацьовує Debounce-таймер (500 мс).
2. UI викликає метод `updateChapterContent(chapterId, html, words, chars)` з Data Access Layer (`client.js`).
3. DAL передає відкритий текст у `cryptoService.encryptChapterContent()`.
4. Сервіс генерує новий унікальний 96-бітний CSPRNG IV, шифрує текст алгоритмом AES-256-GCM, формує 128-бітний Auth Tag та пакує в конверт `ENC:v1:AES-256-GCM:<IV>:<CT>:<TAG>`.
5. DAL записує зашифрований рядок у стовпець `body`, а відкриті лічильники `words_count` та `chars_count` — у відповідні числові стовпці таблиці `chapters` параметризованим SQL-запитом.
6. База повертає успіх -> UI оновлює індикатор на "Збережено".

### 3.2 Потік завантаження розділу з контролем цілісності:
1. `EditorScreen` запитує розділ через `getChapterById(chapterId)`.
2. DAL зчитує рядок із SQLite та передає вміст стовпця `body` у `cryptoService.decryptChapterContent()`.
3. Сервіс перевіряє префікс `ENC:v1:AES-256-GCM:`, парсить IV, шифротекст та Auth Tag.
4. Виконується розшифрування та верифікація Auth Tag:
   - **Успіх:** Відкритий текст повертається до DAL та передається в UI для відображення у редакторі.
   - **Порушення цілісності (фальсифікація або бітові спотворення):** Викидається помилка `"Integrity check failed: data tampered"`, DAL блокує підроблений контент, а UI відображає сповіщення про загрозу безпеці.

### 3.3 Потік експорту книги в DOCX:
1. Користувач натискає "Експорт в DOCX" -> UI викликає `exportBook()` із сервісного шару (`bookExport.js`).
2. **Перевірка прав:** `assertFeature(EXPORT_DOCX)` перевіряє підпис ліцензії публічним ключем і термін дії; для Free кидається `LicenseRequiredError` (`LICENSE_REQUIRED`), запис на диск не виконується, UI показує повідомлення про необхідність Pro.
3. Сервіс отримує розділи через DAL (які автоматично розшифровуються та проходять перевірку цілісності).
4. Сервіс очищає назву файлу через `sanitizeFileName()` та екранує текст через `escapeXml()`.
5. За допомогою `jszip` у пам'яті будується архів OpenXML `.docx`.
6. Обчислюється SHA-256 вмісту, файл записується на диск через `expo-file-system`, зчитується назад і звіряється хеш (MDC); створюється sidecar `.sha256`.
7. Відкривається системний діалог `expo-sharing`.

### 3.4 Потік активації Pro-ліцензії:
1. Користувач вводить (або обирає тестовий) підписаний ключ у «Налаштування → Ліцензія та цілісність».
2. `activateLicenseToken()` декодує base64-JSON, перевіряє структуру полів, RSA-підпис за публічним ключем і `expiresAt`.
3. **Успіх:** об'єкт зберігається в `auth_settings`, UI показує тариф Pro. **Відмова** (`MALFORMED`, `BAD_SIGNATURE`, `EXPIRED`): нічого не зберігається, тариф залишається Free.

## 4. Архітектурні рішення (ADR Summary)

- **ADR-1 (SQLite замість AsyncStorage):** Обрано `expo-sqlite` для підтримки реляційних зв'язків між книгами та розділами, автоматичного підрахунку статистики та каскадного видалення.
- **ADR-2 (Генерація DOCX на клієнті через JSZip):** Експорт реалізується прямо на пристрої без використання зовнішніх серверів конвертації.
- **ADR-3 (Debounced Autosave):** Текст автозберігається з затримкою 500 мс для оптимізації кількості записів на диск.
- **ADR-4 (Автентифіковане шифрування AEAD AES-256-GCM):** Для збережених авторських рукописів впроваджено режим AES-256-GCM замість простих режимів ECB/CBC/CTR. Це гарантує одночасно конфіденційність та криптографічний захист від підробки/модифікації даних через 128-бітний Auth Tag.
- **ADR-6 (Ліцензія з асиметричним підписом замість симетричного секрету):** Підпис ліцензії перевіряється RSA-публічним ключем; симетричний ключ (HMAC) у клієнті означав би, що будь-хто, хто його витягне зі збірки, зможе випускати ліцензії. З публічним ключем витік клієнтського коду не дозволяє підробляти ліцензії.
- **ADR-7 (Fail-safe до Free):** Помилки верифікації ліцензії ніколи не підвищують права; діє принцип «дозволено лише те, що підтверджено».
- **ADR-10 (Структурований JSON-журнал без зовнішніх залежностей):** JSON Lines із єдиним набором полів і UTC-часом дозволяє машинний аналіз і кореляцію без агрегатора; власний мінімальний логер усуває ризик ланцюга постачання та гарантує, що санітизація не обходиться окремими транспортами.
- **ADR-11 (Fail-closed відновлення):** відновлення починається лише після успішної верифікації SHA-256 усіх файлів; часткове відновлення з підозрілої копії гірше за відмову (прихована порча даних).
- **ADR-5 (Заборона Nonce Reuse):** Для кожного шифрування обов'язково генерується унікальний 96-бітний початковий вектор (IV) через CSPRNG, що запобігає компрометації гами шифру при відомому відкритому тексті.

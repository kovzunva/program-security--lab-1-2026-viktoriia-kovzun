> Ця політика визначає обов’язкові вимоги до коду, безпеки та архітектури мобільного застосунку **Writer Editor** (React Native / Expo). Додаток проектується як автономний оффлайн-редактор книг з можливістю аналізу статистики тексту та експорту у формати DOCX/TXT. Ключові вимоги: збереження даних у локальній БД SQLite, розділення шарів, відсутність чутливих даних у коді та обов'язковий аудит npm-залежностей.

## Правила зміни політики

- **Жодних змін мимохідь** — політика не змінюється як побічний ефект розробки фічі; зміни вносяться лише окремою задачею на оновлення політики.
- **Обов'язковий апрув** — будь-яка зміна попередньо погоджується з керівником проєкту.
- **Окремий комміт + інкремент версії** — зміни політики йдуть окремим git-коммітом з префіксом `[POLICY]` у повідомленні та підняттям версії документа.

## Скоуп

Ця політика поширюватиметься на увесь вихідний код мобільного застосунку (`App.js`, папка `src/`) та конфігураційні файли. Вона є обов'язковою для виконання при розробці та підтримці проєкту.

## Технології

- **Node.js** (версія 18+)
- **React Native** (на базі **Expo SDK**)
- **Expo SQLite** (локальна реляційна базова даних)
- **Expo FileSystem** & **Expo Sharing** (робота з файлами та системним меню поширення)
- **React Navigation** (маршрутизація екранів)
- **react-native-pell-rich-editor** (візуальний Rich Text редактор)
- **JSZip** (генерація файлових контейнерів `.docx`)
- **npm** (пакетний менеджер)
- **Git** (система контролю версій)

## Фундаментальні принципи

- **Offline-First та автономність.** Усі дані користувача (книги, розділи) повинні зберігатися локально на пристрої у БД SQLite (`writer-editor.db`). Застосунок не повинен залежати від наявності Інтернету.
- **Розділення шарів (Separation of Concerns).** Компоненти UI не повинні містити прямих SQL-запитів чи файлових операцій. Уся робота з даними виноситься в окремі сервіси та Data Access Layer (`src/database/client.js`).
- **Принцип найменших привілеїв.** Додаток має запитувати лише необхідні дозволи ОС (наприклад, доступ до галереї для обкладинки).
- **Санітизація вводу.** Будь-який текст користувача перед експортом у `.docx` повинен екрануватися від XML-тегів, щоб уникнути пошкодження файлів.

## Архітектура та структура проєкту

Планується наступна структура папок `src/`:

```
src/
├── components/       # Перевикористовувані UI-елементи (модальні вікна, кнопки, кезші)
├── constants/        # Константи проєкту (маршрути ROUTES)
├── database/         # Data Access Layer (client.js — маніпуляції з SQLite)
├── hooks/            # Користувацькі React-хуки (наприклад, орієнтація екрана)
├── localization/     # Файли локалізації (uk, en, de)
├── navigation/       # Конфігурація навігатора (AppNavigator)
├── screens/          # Екрани (Library, BookDetails, Editor, Stats, Settings...)
├── services/         # Сервіси бізнес-логіки (bookExport.js — генерація файлів)
└── theme/            # Теми та палітра кольорів
```

## Політика розкриття та виправлення вразливостей (Vulnerability Disclosure Policy)

- **Звіт про вразливості:** У разі виявлення дефекту безпеки (витік тимчасових файлів, можливість SQL-ін'єкції) створюється приватний баг-репорт.
- **Пріоритети:** Критичні помилки (пошкодження БД, некоректна робота WebView) виправляються першочергово у хотфікс-гілках.

## Політика збереження локальних даних та API-ключів

- **Параметризація SQL-запитів:** Пряма конкатенація рядків у SQL-запитах **заборонена**. Усі запити мають використовувати параметри `?` через `expo-sqlite`.
- **API-ключі:** Додаток проектом не передбачає використання зовнішніх API. У разі додавання хмарних сервісів секрети повинні зберігатися в змінних оточення (`.env`), а не в коді JS.

## Безпека мережевих викликів та експорту файлів

- **Екранування XML при експорті:** При формуванні файлу `.docx` текст обов'язково проганяється через функцію екранування символів `&`, `<`, `>`, `"`, `'`.
- **Санітизація імен файлів:** Назва книги для експортованого файлу очищається від спеціальних символів операційної системи.

## Політика неймінгу

- Компоненти та екрани — `PascalCase` (`LibraryScreen.js`, `ConfirmActionModal.js`).
- Утиліти та сервіси — `camelCase` (`bookExport.js`, `client.js`).
- Константи — `UPPER_SNAKE_CASE` або `PascalCase` об'єкти.

## Політика анотацій (JSDoc)

Публічні сервісні функції повинні супроводжуватися стислими JSDoc-коментарями з описом аргументів та типу поверненого значення.

## Політика винятків та обробки помилок

- Збої при роботі з БД чи файлами не повинні приводити до "вильоту" (падіння) додатка.
- У UI користувачеві показуються зрозумілі повідомлення про помилку (Toast/Alert), без виведення системних стек-трейсів.

## Політика оновлення залежностей та аудиту (npm audit)

- Перед релізом обов'язково виконується `npm audit`.
- Виявлені вразливості залежностей оновлюються через `npm audit fix` або вручну в `package.json`.

## Політика тестування

- Ручне тестування основних сценаріїв (створення книги, додавання розділів, редагування тексту, експорт).
- Перевірка експортованих `.docx` та `.txt` файлів у стандартних офісних програмах.

## Git Workflow

- Основна гілка — `main` або `master`.
- Для нових фіч використовуються гілки `feature/<назва>`, для багфіксів — `fix/<назва>`.
- Префікси коммітів: `[FEAT]`, `[FIX]`, `[DOCS]`, `[POLICY]`.

## Політика документації розробки

Документація проєкту зберігається в папці `docs/` в форматі Markdown і підтримується в актуальному стані під час розробки.

## Анти-патерни

| # | Анти-патерн | Опис | Як правильно |
|---|---|---|---|
| 1 | Прямі SQL-запити в UI | Виклик SQL прямо з екранів. | Виносити операції в `src/database/client.js`. |
| 2 | Склеювання SQL-рядків | `SELECT * FROM books WHERE title = '` + t | Використовувати плейсхолдери `?`. |
| 3 | Сирий XML у DOCX | Вставка тексту користувача у XML без екранування. | Проганяти через `escapeXml()`. |
| 4 | Храніння секретів у коді | Хардкод токенів/ключів. | Використовувати `.env` чи SecureStore. |

## Purpose

Метою цієї політики є встановлення обов'язкових вимог та правил безпечної розробки мобільного застосунку **Writer Editor**, спрямованих на запобігання витоку даних користувачів, забезпечення цілісності авторського контенту (книг, розділів, метаданих), захист від SQL-ін'єкцій та пошкодження форматів при експорті, а також мінімізацію ризиків вразливостей у сторонніх залежностях.

**Основні безпекові цілі проєкту:**
- Забезпечення цілісності та конфіденційності авторських текстів у локальній базі даних SQLite.
- Унеможливлення SQL-ін'єкцій при роботі з локальним сховищем `expo-sqlite`.
- Захист згенерованих OpenXML-контейнерів (`.docx`) від XML-ін'єкцій та пошкодження структури.
- Захист файлової системи від атак типу Path Traversal при формуванні назв експортованих файлів.
- Дотримання принципу Offline-First та мінімізація збору даних без необґрунтованої передачі інформації у зовнішні мережі.

Політика поширюється на всі етапи життєвого циклу застосунку: проектування, розробку, тестування, збірку релізних артефактів та підтримку.

## Scope

Політика поширюється на:
- Увесь вихідний код мобільного застосунку в репозиторії (`App.js`, папка `src/`: екрани, UI-компоненти, шар доступу до даних DAL, сервіси експорту, навігація, хуки, конфігурація тем та локалізацій).
- Конфігураційні файли проєкту (`app.json`, `package.json`, `package-lock.json`, `.babelrc`).
- Інструменти та конфігурації автоматизованого тестування і лінтингу.
- Проектну документацію в папці `docs/`.

**Учасники, зобов'язані дотримуватися політики:**
- Розробники та рев'юери проєкту.
- ШІ-агенти та автономні помічники (наприклад, Antigravity / GitHub Copilot), що виконують генерацію або модифікацію коду.

**Явні виключення зі скоупу:**
- Внутрішня реалізація ядра операційних систем (Android OS / iOS Security Sandbox).
- Апаратна безпека мобільних пристроїв користувача.
- Внутрішня реалізація зовнішніх застосунків (месенджери, поштові клієнти, хмарні диски), у які користувач передає згенеровані файли через системне меню `Expo Sharing`.

## Roles and Responsibilities

- **Власник проєкту / Lead Developer:**
  - Затверджує політику безпеки, модель загроз та специфікацію вимог.
  - Погоджує винятки з вимог безпеки та приймає залишковий ризик.
  - Контролює процес релізу та затверджує критичні зміни в архітектурі.

- **Розробник (Developer):**
  - Відповідає за строге дотримання правил безпечної реалізації коду (параметризація SQL, екранування XML, санітизація імен файлів).
  - Забезпечує обробку помилок у UI без виведення системних стек-трейсів.
  - Проводить попереднє тестування власних змін та оновлює документацію.

- **Рев'юер (Reviewer):**
  - Перевіряє Pull Request на відповідність цій політиці безпеки.
  - Блокує злиття коду при виявленні непараметризованих SQL-запитів, прямих маніпуляцій з неуправльованими файловими шляхами чи хардкоду секретів.

- **ШІ-агент (AI Coding Assistant):**
  - Виконує генерацію та рефакторинг коду СТРОГО відповідно до правил цієї політики.
  - Не має права самостійно послаблювати безпекові вимоги, видаляти модальні вікна підтвердження або міняти параметризовані SQL-запити на рядкову конкатенацію.

## Security Principles

- **Offline-First & Local Data Sovereignty:** Усі дані користувача зберігаються виключно локально на пристрої у БД SQLite (`writer-editor.db`). Застосунок функціонує без вимоги мережевого з'єднання та не надсилає фонову телеметрію.
- **Least Privilege (Принцип найменших привілеїв):** Застосунок запитує лише мінімально необхідні системні дозволи ОС (наприклад, доступ до системного вибору зображень `Expo ImagePicker` для обкладинки книги).
- **Defense in Depth (Глибока оборона):** Вхідні дані перевіряються та обробляються на кількох рівнях: валідація формату в UI, очищення в сервісах (`escapeXml`, `sanitizeFileName`) та параметризація на рівні Data Access Layer (`client.js`).
- **Secure by Default & Fail Securely:** При збоях у роботі з базою даних або файловою системою застосунок не падає ("вилітає"), а повертається до безпечного стану з відображенням зрозумілого повідомлення користувачеві.
- **Minimize Attack Surface:** Мінімізація зовнішніх npm-залежностей. Відсутність невикористовуваних нативних модулів або відкритих мережевих портів.
- **No Secrets in Source Code & Secure Password Hashing:** Заборонено зберігати будь-які токени, ключі, відкриті паролі чи PIN-коди у вихідному коді, конфігураційних файлах або базі даних SQLite. PIN-коди користувачів обробляються виключно через криптографічні солені хеші (алгоритм `bcryptjs`, cost factor ≥ 10).
- **Authenticated Encryption & Integrity by Design:** Усі операції шифрування авторських матеріалів Data-at-Rest обов'язково повинні використовувати автентифіковані режими (AEAD: AES-256-GCM). Будь-яке шифрування без контролю цілісності та автентичності мітки суворо заборонено.
- **Nonce Freshness & Cryptographic Randomness:** Початкові вектори (IV/Nonce) генеруються виключно через криптографічно стійкі генератори псевдовипадкових чисел (CSPRNG) і повинні бути унікальними для кожної окремої операції збереження.
- **Signed Licenses & No Private Keys in Client:** Права тарифу Pro підтверджуються лише цифровим підписом ліцензії, що перевіряється публічним ключем розробника. Приватні ключі підписання ліцензій та релізів **суворо заборонено** вшивати в клієнтський застосунок, репозиторій або збірку.
- **Zero-Trust до клієнта:** Клієнтський застосунок та його середовище вважаються недовіреними. Заборонено довіряти прапорцям ролей/тарифу, `ownerId` чи будь-яким іншим полям, що надійшли від клієнта. Кожен захищений ендпоінт **зобов'язаний** перевіряти Bearer-токен (підпис, `exp`, `typ`) і визначати права лише за його claims та серверним сховищем; доступ до ресурсів завжди обмежується `ownerId === token.sub`. Клієнтські перевірки тарифу — лише UX. Токени зберігаються тільки в SecureStore, обмін — виключно по HTTPS (TLS 1.3 у production); секрет підпису токенів (`JWT_SECRET`) і TLS-ключі не потрапляють у репозиторій чи клієнтську збірку.
- **Explicit Trust Boundaries:** Чітке розмежування меж довіри між недовіреним вводом користувача, WebView-редактором Rich Text, пісочницею додатку та системним меню поширення файлів.

## Secure Development Environment

- **Контроль версій та Git Workflow:**
  - Прямі зміни в захищену гілку `main` заборонені.
  - Усі зміни інтегруються через Pull Requests з обов'язковим рев'ю.
  - Використовуються стандартизовані префікси комітів: `[FEAT]`, `[FIX]`, `[DOCS]`, `[POLICY]`, `[SEC]`.
- **Управління секретами:**
  - Файли конфігурації оточення (`.env`), тимчасові файли та збірки додаються у `.gitignore`.
  - Повна заборона додавання hardcoded ключів або паролів у код (`No Hardcoded Secrets`).
- **Робота із залежностями:**
  - Фіксація версій пакетів у `package-lock.json`.
  - Додавання нової npm-залежності вимагає перевірки її популярності, ліцензії (MIT/Apache 2.0) та відсутності відомих вразливостей.
  - Обов'язкове виконання `npm audit` перед збіркою релізів.
- **Використання ШІ-інструментів:**
  - Інструкції та обмеження з політики передаються в контекст ШІ-агентів. Вигенерований ШІ код підлягає обов'язковій валідації на відсутність анти-патернів.

## Software Protection

- **Захист вихідного коду:** Репозиторій розміщено на захищеному хостингу (GitHub) з обмеженням прав доступу.
- **Цілісність релізних артефактів:** Релізні збірки (APK/AAB/IPA) формуються через інструментарій Expo (EAS Build або локальний Expo CLI) із використанням захищених цифрових підписів і ключів підписання.
- **Захист ключів підписання:** Приватні ключі підписання (Android Keystore / iOS Distribution Certificates) зберігаються поза репозиторієм у захищеному сховищі ключів.
- **Мінімізація чутливих даних у логах:** Заборонено виводити повні тексти книг, розпарсені структури чи системні стеки помилок у підсумкові виробничі логи.

### Модель розповсюдження (Freemium)

- **Free:** базове редагування книг та експорт у `.txt` — безкоштовно, без реєстрації й без мережевих перевірок.
- **Pro:** експорт у форматований `.docx`, детальна статистика та шифрування розділів — за чинною підписаною ліцензією.
- Перевірка ліцензії виконується повністю офлайн (Offline-First): без «phone-home» і без передавання даних користувача для валідації.
- Прострочена, пошкоджена або непідписана ліцензія тимчасово повертає тариф Free; **дані користувача при цьому не блокуються і не видаляються** — доступ до вже створених книг і експорт у `.txt` зберігаються завжди.

### Підписування релізних збірок (Code Signing) та ліцензій

- Кожна релізна збірка (Android APK/AAB, iOS IPA) підписується ключем розробника (Android Keystore / Apple Distribution Certificate) через EAS Build або локальний Expo CLI; непідписані збірки не розповсюджуються.
- Хеші SHA-256 релізних артефактів публікуються разом із релізом для незалежної перевірки цілісності завантаження.
- Ключі підписання збірок і ключ підписання ліцензій зберігаються поза репозиторієм (захищене сховище EAS Credentials / KMS / HSM / офлайн-носій), доступ — лише у Власника проєкту; файли `*.jks`, `*.p12`, `*.key`, `*.pem` виключені через `.gitignore`.
- **Заборона вшивання приватних ключів:** у вихідному коді, ресурсах, `app.json`, змінних `EXPO_PUBLIC_*` та бандлі застосунку допускається лише **публічний** ключ верифікації. У разі витоку приватного ключа підписання він негайно відкликається, генерується нова пара, публікується оновлення застосунку з новим публічним ключем.
- Демонстраційний підписаний ключ (ЛР №5) видається утилітою `tools/sign_demo_license.js`, яка генерує одноразову пару ключів у пам'яті й не зберігає приватний ключ.

## Secure Implementation

- **Криптографічний захист та контроль цілісності (Cryptographic Policy):**
  - **Заборона незахищених режимів шифрування:** Суворо **ЗАБОРОНЕНО** застосування режиму електронної кодової книги (ECB — Electronic Codebook), оскільки він не приховує патерни відкритого тексту.
  - **Заборона неавтентифікованих режимів (CTR / CBC без MAC):** Суворо **ЗАБОРОНЕНО** застосування симетричних шифрів (CTR, CBC, потокових шифрів) без механізму автентифікації повідомлень (HMAC/GMAC). Неавтентифіковані режими піддаються атакам бітової підміни (Bit-flipping Attack) та атакам відновлення гами за відомим відкритим текстом (Known-Plaintext Attack), як це продемонстровано в рамках Лабораторної роботи №4.
  - **Обов'язковість AEAD (AES-256-GCM):** Для шифрування авторських матеріалів (`chapters.body`) використовується виключно алгоритм автентифікованого шифрування AES-256-GCM.
  - **Вимога унікальності IV для кожної операції (Nonce Reuse Prohibition):** Для кожного шифрування тексту генерується унікальний 96-бітний початковий вектор (IV) за допомогою CSPRNG. Повторне застосування однакового вектора для одного ключа категорично заборонено.
  - **Обов'язкова перевірка Auth Tag:** Під час дешифрування модуль зобов'язаний валідувати 128-бітну мітку автентичності. При будь-якій розбіжності операція блокується з викликом помилки `"Integrity check failed: data tampered"`.
  - **Управління ключами та виключення Hardcoded Secrets:** Ключі формуються через CSPRNG або виводяться за стандартом PBKDF2 (HMAC-SHA256, 10 000+ ітерацій) на базі випадкової солі та PIN автора. Вшивання ключів у вихідний код заборонено. Підтримується безпечна ротація ключів через `cryptoService.rotateKey()`.
- **Валідація та санітизація даних:**
  - **Текст користувача:** Текст перед формуванням XML-структур у файлі `.docx` обов'язково обробляється функцією `escapeXml()`, яка замінює спецсимволи `&`, `<`, `>`, `"`, `'` на відповідні XML-сутності.
  - **Назви файлів:** Для запобігання Path Traversal при збереженні назви книг очищаються функцією `sanitizeFileName()`, яка видаляє управляючі символи та спецсимволи ОС (`/`, `\`, `:`, `*`, `?`, `"`, `<`, `>`, `|`).
  - **Rich Text HTML:** Текст із `RichEditor` під час конвертації в звичайний текст проганяється через утиліту `richHtmlToPlainText()`.
- **Безпечна робота з базою даних (SQLite):**
  - Пряма конкатенація рядків у SQL-запитах **СТРОГО ЗАБОРОНЕНА**.
  - Усі SQL-запити в `src/database/client.js` виконуються виключно із застосуванням параметризованих запитів з плейсхолдерами `?`.
  - Для забезпечення цілісності та запобігання блокуванням БД при ініціалізації вмикається режим `PRAGMA journal_mode = WAL;` та вмикається підтримка зовнішніх ключів `PRAGMA foreign_keys = ON;`.
- **Безпека WebView (Rich Text Editor):**
  - WebView-компонент `react-native-pell-rich-editor` ізолюється від нативного мосту та локальної файлової системи пристрою.
- **Обробка помилок та логування:**
  - Усі виклики SQLite та файлової системи загортаються в блоки `try/catch`.
  - Користувачеві відображаються локалізовані та зрозумілі повідомлення про помилку через UI-компоненти (Toast / Alert), без демонстрації сирих помилок бази даних чи стек-трейсів.

## Security Verification

- **Code Review:** Кожен Pull Request перевіряється на відсутність порушень правил безпечної реалізації (усі SQL-запити перевіряються на параметризацію, а операції з файлами — на санітизацію шляхів).
- **Статичний аналіз коду:** Використання ESLint для перевірки синтаксису, потенційних багів та невикористовуваного коду.
- **Сканування залежностей:** Виконання `npm audit` у процесі розробки та перед кожним релізом. Виявлені вразливості рівня `High` та `Critical` підлягають негайному усуненню.
- **Автоматизоване та ручне безпекове тестування:**
  - Тестування граничних значень: введення в назви та текст символів кавички, спецсимволів XML, SQL-ін'єкцій (`' OR 1=1 --`), довгих рядків.
  - Перевірка коректності експорту та відкриття згенерованих `.docx` файлів у MS Word / LibreOffice.
  - Перевірка функціонування модальних вікон підтвердження `ConfirmActionModal` при видаленні книг та розділів.
- **Release Gate:** Реліз блокується, якщо в коді наявні незатверджені винятки або непідтверджені вразливості залежностей високого рівня.

## Vulnerability Management

- **Джерела виявлення:** Результати `npm audit`, сповіщення GitHub Dependabot, результати внутрішнього тестування або звернення користувачів.
- **Реєстрація та класифікація:** Усі виявлені дефекти безпеки реєструються в баг-трекері із присвоєнням рівня критичності:
  - **Critical:** Можливість пошкодження всієї БД SQLite, виконання довільного коду в WebView, витік даних.
  - **High:** XML-ін'єкція у експортований файл, Path Traversal при збереженні.
  - **Medium/Low:** Некоректне відображення помилки, неоптимальний Debounce.
- **Строки виправлення:**
  - Вразливості рівня `Critical` та `High` усуваються протягом 48 годин у хотфікс-гілках.
  - Вразливості `Medium` та `Low` усуваються у плановому порядку в наступному спринті/релізі.
- **Аналіз причин (Root Cause Analysis):** Після усунення критичної вразливості проводиться аналіз причин її виникнення, а за потреби оновлюється модель загроз та правила цієї політики.

## Logging and Monitoring

- **Обов'язковий аудит:** усі запити до серверного API та події безпеки (вхід, відмова 401/403, replay refresh-токена, брутфорс, операції резервного копіювання) фіксуються в `logs/security.log` у форматі JSON Lines (UTC, `requestId`, actor, action, resource, outcome). Деталі — `docs/architecture-spec-42010.md`, п. 2.8.
- **Заборона записувати секрети:** паролі, PIN, `client_secret`, повні токени в журнал не потрапляють (санітизація на рівні логера); порушення вважається інцидентом безпеки рівня High.
- **Ротація та зберігання журналів:** ротація за розміром 1 МБ, 5 архівів; для production журнали зберігаються ≥ 90 днів на окремому хості, доступ — лише ролі Admin.
- **Реагування на алерти:** `WARNING` розглядається протягом робочого дня; `CRITICAL` (брутфорс ≥ 10 спроб/хв, провал верифікації копії) — негайно (≤ 1 година): блокування IP/облікового запису, перегляд журналу за `requestId`.

## Backup and Disaster Recovery

### Політика резервного копіювання

| Параметр | Значення |
|---|---|
| Правило **3-2-1** | **3** копії даних (робоча + 2 резервні), **2** різні носії (локальний диск + зовнішній/хмарний носій), **1** копія поза основним майданчиком (offsite, зашифрована) |
| Повні копії | щодня (`node scripts/backupManager.js backup`) та перед кожним релізом/міграцією схеми БД |
| Інкрементні копії | щогодини (зміна файлів відносно останньої повної за SHA-256 з `manifest.json`); *поточна реалізація CLI виконує повні копії — інкрементний режим є цільовим розширенням, до його появи щогодинна повна копія забезпечує RPO* |
| Строки зберігання | щогодинні — 48 год; щоденні — 14 днів; щотижневі — 8 тижнів; щомісячні — 12 місяців (`backupManager.js prune <N>` видаляє найстаріші) |
| **RPO** | **1 година** — максимальна допустима втрата даних |
| **RTO** | **15 хвилин** — максимальний час відновлення сервісу |
| Захист копій | вміст — шифротекст AES-256-GCM; ключі зберігаються окремо від копій; доступ до `backups/` лише власнику; `backups/`, `logs/`, `data/` виключені з Git |
| Контроль цілісності | SHA-256 кожного файлу в `manifest.json`; копія без успішної верифікації вважається непридатною |
| Тестування відновлення | `node scripts/dr_simulation.js` — перед кожним релізом, а також щокварталу «навчання» на реальній копії |

### План аварійного відновлення (Disaster Recovery Plan)

**Сценарії:** (A) пошкодження/видалення `writer-editor.db` чи серверного сховища; (B) компрометація сервера (підозра на зміну даних); (C) втрата хоста; (D) шкідливе/помилкове пошкодження самої копії.

| Крок | Дія | Відповідальний | Ціль часу |
|---|---|---|---|
| 1. Виявлення | Алерт `CRITICAL`/`ERROR` у журналі, помилка перевірки цілісності сховища, скарга користувача; фіксація часу інциденту | Admin | ≤ 5 хв |
| 2. Локалізація | Зупинити сервіс (`apiServer`), якщо ризик подальшого пошкодження; зберегти журнали та пошкоджені файли як докази; для сценарію B — відкликати токени (змінити `JWT_SECRET`) | Admin | ≤ 5 хв |
| 3. Вибір копії | Обрати найновішу копію до моменту інциденту (`backups/backup_<ts>`); для сценарію C — з offsite-носія | Admin | ≤ 2 хв |
| 4. Відновлення | `node scripts/backupManager.js restore <шлях>`: верифікація SHA-256 → відновлення → пост-перевірка. Код виходу 2 / `CRITICAL` = копія пошкоджена → взяти попередню (сценарій D) | Admin | ≤ 3 хв |
| 5. Перевірка | Запуск сервісу, тест входу й синхронізації, перегляд `security.log`; клієнти повторно синхронізують дані з пристроїв | Admin / Dev | ≤ 5 хв |
| 6. Після інциденту | Root Cause Analysis, оновлення моделі загроз, фіксація фактичних RPO/RTO, за потреби повідомлення користувачів | Lead Developer | ≤ 5 діб |

Сумарно кроки 1–5 вкладаються в **RTO = 15 хв**; втрата даних обмежена інтервалом між копіями (**RPO = 1 год**). Локальна SQLite-база на пристрої користувача відновлюється з шифрованого серверного конверта (опційна синхронізація, FR-7.6) або з експорту `writer-editor.db`.

- **Затвердження:** Виняток вважається прийнятим лише після письмового затвердження Власником проєкту (Lead Developer).
